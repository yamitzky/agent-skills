# deep-explain

## Overview

ユーザーが `/deep-explain` を呼んだら、対象を **4つの原則** に従って説明し直す。Claude は放っておくと「前のターンからの差分」や、日本語に英単語を混ぜた書き方（ルー語）・その場ででっち上げた造語を散りばめただけの要約に逃げがちで、それが当人にしか分からない説明になる。このスキルは、その逃げを禁止して、誰が読んでも分かる説明を強制する。

原則のうち最初の3つは **書き方（文体）** の規律、4つ目は **どこに分量を寄せるか（配分）** の規律。文体だけ整えても、肝心な部分が薄ければ説明として失敗する。両方を揃えて初めて通じる。

ただし、**消したいのは「読者が知らない言葉」であって、技術用語そのものではない**。一般に広く使われている技術用語は、噛み砕かずそのまま使う方がむしろ読みやすい。

また、**社内で共通認識として使われている用語（社内システム名・独自の略語など）は、そのまま使ってよい**。禁止したいのは AI がその場でこしらえた造語であって、実際にチームで通じている呼び名ではない。そうした社内・案件固有の固有名詞は、本文ではそのまま使い、応答の末尾に **用語定義セクション** を設けてまとめて意味を添える（後述）。

ユーザーが明示的に `/deep-explain` を呼んだときだけ動く。自動発火はしない。

## 何を説明するか

- **引数あり**（例: `/deep-explain この関数` / `/deep-explain このエラー`）→ 指定された対象を説明する
- **引数なし** → **直前の自分（assistant）の発言** を説明し直す

## 4つの原則（絶対）

原則1〜3は **文体**（書き方）の規律、原則4は **配分**（どこに分量を寄せるか）の規律。

### 1. その応答だけで完結する

読者は会話の履歴を持っていない前提で書く。「先ほどの」「さっきの修正」「前述の通り」のような、前のターンを参照する語を使ってはいけない。説明に必要な事実は、たとえ直前に書いたことでも、その応答の中にもう一度書く。

会話の外にある内部事情（過去のやり取り、メモリ、内部ルールなど）を理由として持ち出さない。読者はそれを知らない。

### 2. 前提知識ゼロの人に向けて、背景と理由から書く

結論や「やったこと」だけを並べない。**なぜそうなるのか / なぜそれが問題なのか** を、背景から順に説明する。

ここでの「前提知識ゼロ」は、**その会社・プロジェクト・案件の事情を知らない** という意味で、コンピュータ一般の知識がゼロという意味ではない。だから、その組織・案件に固有の固有名詞（社内システム名、製品コード名、独自の略語）は「何であるか」を一言添える。一方、世間に広く知られた固有名詞（Chrome、Google、iPhone など）に説明は要らない。

「その組織の中の人なら通じる」書き方は失敗とみなす。

### 3. 言葉で説明する（ルー語・AI造語の禁止）

禁止するのは **読者が知らない言葉** と **その場ででっち上げた造語** であって、技術用語や実際にチームで通じている呼び名そのものではない。

**やめるべきもの:**

- **ルー語**: 日本語の文に英単語を動詞・名詞のまま混ぜる書き方（「sidebar を show して」「データを fetch する」「diff を取る」）。これは普通の日本語にする（「サイドバーを表示して」「データを取得する」「変更点を見比べて」）。
- **AI造語**: その場の説明のために Claude が勝手にこしらえた呼び名・略語。実在しない概念名をでっち上げてはいけない。説明したい中身は、既存の言葉で素直に書く。

**そのまま使ってよいもの:**

- **一般に広く使われている技術用語**: Chrome の拡張機能、サイドバー、API、データベース、サーバー、ブラウザ など。いちいち「Google Chrome（ウェブ閲覧ソフト）」のように噛み砕かない。冗長になって、かえって読みにくくなる。
- **社内で共通認識のある用語**: 社内システム名、チームで定着した独自の略語、案件のコード名など。これらは実際に通じている言葉なので本文ではそのまま使う。ただし読者（プロジェクト外の人）は知らないので、**用語定義セクション**（後述）にまとめて意味を添える。

判断基準: **その言葉は、実際に組織やチームの中で通じているか。** 通じているならそのまま使い、固有名詞なら用語定義に載せる。誰にも通じない・Claude がその場で作っただけなら、使わずに普通の言葉で書き直す。

例: 「sidebar を show して」→「サイドバーを表示して」（ルー語）。「app-uploader に投げる」→ `app-uploader` はそのまま使い、用語定義に「app-uploader: アプリを配信用に変換して送り出す社内の仕組み」と載せる。「stg に apply 済み」→「stg には反映済み」と書き、用語定義に「stg: 本番の手前の検証用環境」と載せる。

### 4. 焦点に分量を寄せる（配分の規律）

原則1〜3が「どう書くか」なら、これは **「どこを厚く書くか」**。文体を整えても、読者が一番知りたい部分が薄ければ説明は成立しない。次の3つを守る。

**(a) 指摘された箇所を中心に据える（再呼び出し時）。**
ユーザーが直前に「ここが分からない／足りない」と指摘して再度 `/deep-explain` を求めたなら、**指摘された当の箇所を説明の中心に置き、そこに最大の分量を割く**。背景・前提は、その箇所を判断するのに要る分だけに削る。

> 原則2「背景と理由から書く」を、不足箇所を薄いままにする言い訳に使わない。背景を手厚く展開して仕事をした気になり、肝心の指摘箇所を元の薄さで素通りするのは、この原則への違反。背景を厚くすることと、焦点を厚くすることは別物。求められているのは後者。

**(b) 比較するなら各項目を同じ密度で書く（比較の対称性）。**
複数の選択肢・案・対象を比較するときは、**全項目を同じ密度で揃える**。各項目について「何であるか／どうなるか・なぜそうなるか・短所（トレードオフ）」を、同じ粒度で書く。片方を3段落、もう片方を2行、のように密度が偏ったら、それは比較として壊れている（読者は対称な情報がないと天秤にかけられない）。ラベルの言い換えだけで中身が無いのも、密度ゼロと同じ。

**(c) 焦点を出力の前方に置く。**
読者が一番知りたい部分を末尾に置かない。「背景→前提→結論」と前から積み上げる構成は、前半で体力を使い切って結論側が痩せやすい。焦点（指摘箇所・比較の本体）を先に出し、背景はそれを支えるのに必要な分だけ添える。

## 用語定義セクション

本文で **社内・案件固有の固有名詞**（社内システム名、独自の略語、環境名、案件のコード名など）を使ったら、応答の末尾に「用語定義」セクションを設け、使ったものをまとめて列挙する。

- 対象は **社内・案件固有の固有名詞のみ**。一般的な技術用語（API・サーバーなど）や、世間に広く知られた固有名詞（Chrome・Google など）は載せない。
- 形式は箇条書き。`用語名: 一言の説明` で十分。
- 本文では補足なしでそのまま使ってよい（毎回カッコ書きで開かなくてよい）。読者は用語定義を見れば追える。
- 固有名詞を一つも使っていない応答では、このセクションは不要。無理に付けない。

例:

```
## 用語定義

- app-uploader: アプリを配信用に変換して送り出す社内の仕組み
- stg: 本番の手前の検証用環境
```

## 出力前の自己チェック

出力する直前に、自分の文章を読み返して次を確認する。一つでも当てはまったら直してから出す。

- [ ] 「先ほど」「さっき」「前述」など、前のターンに依存する語が残っていないか
- [ ] ルー語（日本語に混ざった生の英単語）が残っていないか
- [ ] その場ででっち上げた造語（実在しない概念名・略語）を使っていないか
- [ ] 逆に、一般的な技術用語（Chrome・サイドバー・API など）までいちいち噛み砕いて冗長になっていないか
- [ ] 社内・案件固有の固有名詞を使ったなら、末尾の用語定義セクションに載せたか（広く知られた固有名詞は不要）
- [ ] 「なぜ」が抜けて、結論・手順の羅列になっていないか
- [ ] 会話の外の内部事情（メモリ・過去ログ・内部ルール）を前提にしていないか
- [ ] 再呼び出しなら、ユーザーが指摘した箇所が説明の中心になっていて、そこに最大の分量が割かれているか（背景ばかり厚くして指摘箇所を薄いまま素通りしていないか）
- [ ] 複数の選択肢・案を比較しているなら、全項目が同じ密度か（片方だけ厚い／ラベルの言い換えだけで中身が無い、になっていないか）
- [ ] 読者が一番知りたい焦点が末尾に埋もれていないか（背景を積み上げて結論側が痩せていないか）

逆に、**水増しもしない**。丁寧にするためだけの前置き、当たり前の一般論、「お役立ち」的な蛇足は入れない。分かるために必要な分だけ書く。長くするのが目的ではなく、通じるのが目的。

なお、**「水増しするな」と「焦点に分量を寄せろ」は向きが逆だが、両立する**。前者は全体の量を抑える規律、後者は限られた量を必要な箇所に寄せる配分の規律。蛇足を削り、その分を焦点に回す——どちらも「通じるのに必要な配分にする」という一つの目的の両面。

## よくある失敗と直し方

| 失敗 | 直し方 |
|------|--------|
| 「先ほどの修正は…」と書き出す | その応答だけで完結させる。何を修正したのかをこの応答内で一から述べる |
| 「sidebar を show して」「diff を取る」 | 「サイドバーを表示して」「変更点を見比べて」と普通の日本語にする（ルー語の禁止） |
| 一般用語まで噛み砕く（「Google Chrome（ウェブ閲覧ソフト）」） | 「Chrome の拡張機能」でよい。広く通じる技術用語は説明しない |
| 説明のために概念名をでっち上げる | その場の造語をやめ、既存の言葉で素直に書く（AI造語の禁止） |
| `stg`・社内システム名を使ったのに用語定義がない | 本文ではそのまま使い、末尾の用語定義セクションに `stg: 検証用環境` のように載せる |
| 固有名詞を毎回カッコ書きで開いて冗長 | 本文では補足なしで使い、用語定義にまとめる |
| やったことだけ並べる | 「なぜそれが必要だったか」を背景から先に説明する |
| 通じやすさのために前置きを足す | 削る。必要な情報だけ残す |
| 「ここが分からない」と言われた箇所を薄いまま、手前の背景だけ厚くする | 指摘された箇所を中心に据え、そこに最大の分量を割く。背景は判断に要る分だけに削る |
| 比較で片方を3段落・もう片方を2行で書く | 全項目を同じ密度で揃える（何であるか・なぜそうなるか・短所を全項目ぶん） |
| 選択肢の説明がラベルの言い換えだけで中身が無い | 中身（具体的にどうなるか・なぜ・トレードオフ）を書く。言い換えは説明ではない |
| 読者が一番知りたい結論・比較を末尾に置く | 焦点を前方に出し、背景はそれを支える分だけ後ろに添える |

## Red Flags — これを書いていたら止めて書き直す

- 「先ほど」「さっき」「前回」「前述」「上記の通り」
- ルー語（日本語に生の英単語を混ぜる）: 「show して」「fetch する」「apply 済み」「diff を取る」
- その場ででっち上げた造語（実在しない概念名・略語）
- 社内・案件固有の固有名詞（社内システム名・stg / prd / dev など）を使ったのに、末尾に用語定義セクションがない
- 「ご存じの通り」「いわゆる」で内輪の言葉を流す
- 結論だけで「なぜ」がない
- 逆方向: 一般的な技術用語（Chrome・サイドバー・API・サーバーなど）をわざわざ噛み砕いて冗長にしている
- 指摘された箇所より、その手前の背景のほうが厚い（「背景から丁寧に」を、指摘箇所を薄くする言い訳に使っている）
- 比較なのに項目ごとの密度が揃っていない（片方だけ厚い／片方がラベルの言い換えだけ）
- 読者が一番知りたい部分（指摘箇所・比較の本体）が応答の末尾にある

これらが一つでもあれば、原則のどれかに違反している。直してから出す。
